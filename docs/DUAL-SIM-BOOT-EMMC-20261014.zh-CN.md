# 双卡、默认启动提示与 eMMC 调查（2026-10-14）

本轮完成公共代码修正和离线回归，MU300/V50 的网页部分已热部署，后续 E5 也已完成用户态热部署。
后续已按用户要求撤销运行时禁休眠及 `CLK_AUTO` 禁用，当前策略以下文第 3 节为准。
**混合物联卡导致“无模组”的完整原因、V50 旧元数据损坏的唯一底层原因仍未确认。**

## 1. E5 仓库的双卡短信隔离

用户报告：物联卡与普通卡混插，不论卡槽顺序均可能异常；双卡收短信后也有人遇到无网、无模组。
这次连接的实机是 V50，并没有取得上述故障组合的 E5/T551M/M8 日志，不能声称已经复现和根治。

找到的明确缺陷是短信存储索引缺少卡槽归属：

- `+CMTI: "SM",<index>` 没有 SIM 编号。
- 当前接收器已记录：在本平台通过主命令口配置 CNMI，两张卡的 CMTI 可能到达同一个 URC 环；环号不能可靠证明短信来自哪张卡。
- 通用 ModemManager 接收 CMTI 后，直接按该索引发无卡号 CMGR，读取的是当前数据卡的存储。
- 另一条公共接收链路 `e5-sms-receive` 则逐卡查询 CCID、CMGL，并分别持久化、合并分段和转发。两条链路因此可能重复读取，甚至读取另一张卡的同号索引。

新增 `rootfs/deb-patches/modemmanager-15-unisoc-sms-isolation.patch`：

1. 安装了公共双卡接收器时，禁止通用 CMTI 回调进行无卡号索引读取。内核的 `sms_events` 与逐卡接收器继续负责接收；原有 CNMI、状态报告及短信发送保留。
2. 未安装公共接收器的系统保留原回调，不直接取消短信接收能力。
3. 通过 MM 执行的卡槽限定短信查询、删除和设置，在成功或 CMS/CME 失败后，都先恢复数据卡的 AT 通道上下文，再返回结果。
4. CMGS/CMGW 的提示符与 PDU 事务不拆分。这项修正不执行 RF 重启或切换数据卡。

审查补充：卡槽恢复仅用于整条命令都属于安全短信查询/设置的事务，按引号之外的分号逐项检查；复合命令中任意位置含 CMGS/CMGW 或未知命令，均保留原处理，避免在提示符后插入卡槽恢复。已补充复合发送、大小写、引号内分号及畸形命令的回归测试；OpenWrt 包修订号升为 r929，需重新构建和部署才能在实机生效。

缺少 IMS 承载不应单独被视为模块消失。已核对现有 CSCA 查询/回写失败会按非致命结果继续；IMS PDN 的 vendor URC 已有过滤，通用 CGEV 对带 CID 的去激活也按 CID 匹配。
目前没有证据证明 IoT 卡缺少 IMS 就是混插失败的根因，因此没有新增一律关闭 IMS 的策略，也没有把混插与收短信的两种故障判为同一原因。

公共 OpenWrt 包已构建为 `modemmanager-1.24.0-r928.apk`；Debian 构建也通过编号补丁通配列表纳入同一修正。
后续 E5 已部署 MM r928 并确认 Unisoc 插件、CMTI 隔离回调和双卡接收器运行。
对 SIM1/SIM2 分别执行 CNMI 查询后，实际 AT 上下文均恢复到原数据卡 SIM1。
T551M/M8 尚未部署；混合卡、实际来短信及通话的验收仍未完成，不能据此宣称原始故障已根治。

## 2. 两个仓库的临时启动提示

公共看板首页新增提示：当前为临时启动 OpenWrt，是否设为默认启动。E5 仓库的共享屏幕主页也显示相同提示，覆盖 E5、T551M、M8。

- 状态读取各自的 `default-boot` 文件，区别于“当前正在运行哪个 A/B 槽”。没有保存选择时按原有 Android 回退语义提示；非法配置返回 unknown，不伪造确定结果。
- 缺少启动控制素材、受限制的试用镜像禁用设置按钮，并显示原因。
- 网页使用现有主题确认框，补齐中、英、土耳其语。屏幕采用中英文字和二次点按确认，锁屏、息屏时不能触发。
- 用户确认后修改默认启动，不立即重启或切网。下次状态刷新反映保存结果，不增加状态轮询或 AT 请求。
- `boot-status` 在看板进程内以 shell builtin 读取，不读取整份 misc，不启动额外常驻进程。

顺带修正启动控制的写入事务：旧代码先保存 Linux 意图，再写 misc；后者失败会留下错误的默认状态。
现在先暂存配置、备份原 32 字节控制信息，校验写入长度和 misc 回读，成功后再替换配置。
失败时恢复原控制信息和配置；设置与成功启动后的 rearm 使用同一互斥锁，避免互相覆盖。

V50 已部署 6 个相关文件并核对 SHA256。实机独立 `boot-status` 与 `dashboard-info.boot` 均返回：
`default=linux, temporary=false, can_set_default=true`。部署没有改动其启动选择或重启设备。
后续 E5 的网页和屏幕也已部署，二者均正确返回默认 Linux、非临时启动；T551M/M8 尚未部署。

## 3. 公共 eMMC 保护（运行时常驻已撤销）

E5 入口：`devices/common/emmc.py`；MU300 入口：`upstream/port/emmc.py`。两份实现一致。

- 识别非可移除的 MMC 内存宿主，排除 NO_MMC、Wi-Fi SDIO 与 TF/SD 宿主。
- 已撤销宿主 `pm_runtime_forbid`、aggressive PM 能力清除及 runtime 回调直接返回；恢复原有 autosuspend、时钟和 PHY 休眠/恢复路径。
- 已撤销内外 `CLK_AUTO` 禁用，恢复原有空闲自动时钟门控，避免留下运行时常驻的耗电代价。
- 系统休眠保护移入专用的 `mmc_suspend()` 回调：活动 eMMC 先刷缓存再保持卡状态；本来已运行时休眠的卡保持原状态。
- `_mmc_suspend()` 不再包含共用的提前返回，aggressive runtime suspend 能正常执行原有卡休眠/断电。
- 正常关机、驱动移除和欠压处理保留原路径；TF、SDIO 不套用 eMMC 保护条件。
- 清理此前公共常驻及旧 V50/AW9523B 常驻代码，重复处理缓存树不会重新引入禁休眠。

已接入 E5、T551M、M8 的 prepare-kernel，以及公共 Docker/native 构建入口。MU300 的公共 port/install 同样必经此策略。后续机型沿这些公共入口构建即会继承；源码锚点或能力位冲突时构建停止，避免静默遗漏。

另补齐可靠写兼容：E5 已设置 `MMC_CAP2_NO_REL_WR`，MU300 原先没有。新的公共处理让块层以普通写入加缓存刷新的方式实现 FUA 持久化，不直接丢掉 FUA，也不关闭写缓存。
这是一项从 E5 既有路径对齐的兼容保护，不是证明 V50 损坏由 FUA 单独造成。

当前三套最终构建已通过：E5 主线 6.18 的 T551M 配置、MU300 6.18.54、MU300 7.2.8，均构建 Image 和匹配 modules。
E5/M8 的板级完整内核与三个安装包没有在本轮重新打包；新策略未刷入实机。
V50 当前运行的旧 `#17` 仅验证了此前宿主 runtime PM 禁用策略，不能用其正常结果冒充新完整策略的验收。

本次撤销仅修改源码、已准备的构建树和离线构建，没有向实机写入内核或修改 sysfs。
因此 V50 仍运行旧 `#17` 的宿主常驻策略，要改变实机行为仍需部署重新构建的内核。
没有新增轮询，未测量待机电流，也不能保证剩余保护解决所有硬件写入问题。

## 4. V50 inode 不一致：确认到哪一步

历史日志在启动约 9 秒出现 `ext4_lookup: deleted inode referenced`，之后重复报告 49541–49547 等新写入 inode。
目录仍指向这些 inode，但 inode 内容已无效/删除；这说明目录与 inode 元数据版本不一致，而不是“查看目录”的程序删掉了文件。
之前同步后正常重启仍出现新脚本丢失、配置回退，离线 fsck 后也曾复发：fsck 能修现有结构，不能证明底层持久化问题已经解决。

本轮重新只读核对：

| 检查 | 结果 | 能说明什么 |
|---|---|---|
| 根分区 p76 | 起始 37441536 扇区，长度 16777216 扇区 | 与先前通过 CRC 的 GPT 布局一致 |
| EXT4 超级块 | 2097152 × 4096 = 8589934592 字节 | 文件系统正好 8 GiB，与分区相等，无文件系统越界证据 |
| 文件系统 | 直接挂载 p76，带 journal | 不依赖 F2FS userdata 或 loop 镜像 |
| 运行时 PM | 宿主 on/active | 旧 #17 的防自动休眠已生效 |
| 总线 | HS400 enhanced strobe、200 MHz、8 bit | 稳定观察时没有通过降到 HS200 规避问题 |
| 错误计数 | 0，观察时约开机 3548 秒 | 此观察窗口未见新的 EXT4 结构错误 |
| 写缓存/FUA | write back、FUA=1 | 实机仍是新兼容保护部署前的路径 |

此前还确认：已休眠后在 initramfs 设置 `power/control=on` 的恢复实验卡在挂载/fsck 之前；改为 probe 阶段提前禁止休眠后，写入、配置和 SHA256 在正常重启后保留。
这支持宿主恢复链存在问题，但不是某条写请求丢失的完整因果跟踪。
MM/HSQ 的请求路径会通过 `mmc_get_card`/host claim 持有 PM 引用，未发现“request_atomic 没单独取 PM 引用，因此必然在传输中休眠”的简单漏洞，不能拿它作为根因。

现有证据更符合重启前后的元数据持久化/恢复异常；宿主恢复、可靠写及硬件门控是已处理的风险路径。
尚缺失败时的数据块、journal 提交/刷缓存与宿主恢复关联记录，无法区分具体的恢复故障、写顺序/持久化错误或其他存储问题。
**目前不能声称找到了唯一底层根因，也不能保证不会复发。**

### 与 M8 旧问题区分

- M8 内置铃声损坏：已有逐字节证据是构建时把二进制 CRLF 转成 LF；不是 inode 错误的证据。
- 本次找到的旧 EXT4 aborted journal 记录来自 T551M 的 loop 镜像：先发生底层 F2FS SSA/SIT 不一致，随后 loop 写入 I/O 错误和 journal abort。这条因果链与 V50 直接 p76 的现象不同。
- 未在现存 M8 日志找到同样的 deleted-inode 首次故障，不能凭表面相似认定是同一个 bug。
