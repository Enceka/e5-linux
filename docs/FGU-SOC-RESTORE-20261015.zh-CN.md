# E5 关机再开机电量跳到 100%：排查与公共防护

后续：2026-10-16 的第二轮策略方案尚无原厂对照证据，已撤回，见
[原厂行为对照与方案状态](FGU-FULL-CHARGE-20261016.zh-CN.md)。下文保留当时的验证范围。

2026-10-15。用户转述荣悦 E5 偶发关机再开机后电量显示 100%。
其他机型是否受影响未知；本次没有故障 E5 的关机前后原始电量计数据，
不能把以下代码缺陷直接写成该机器已经确认的唯一根因，也没有实机复现或部署。

## 数据链路

网页看板与屏幕都直接读取 `/sys/class/power_supply/battery/capacity`，没有
“读失败就显示 100%”的默认值。该节点由 `charger-manager.c` 提供：

1. FGU 在 PMIC 常供电寄存器中保存两份数据：显示电量、常温电量。
2. 开机恢复显示电量，并用常温电量初始化库仑计。
3. 充电管理器将内部 0～1000 换算为 0～100%，超过 100 的结果截成 100。

此处保留区是 PMIC 的硬件寄存器，不是 SIM/NV 分区，也不需要写 userdata 文件。
库仑计、温度补偿和电量表均保留，不增加定时器、轮询或周期性磁盘写入。

## 确认的代码缺陷

- `ump96xx_fgu_read_last_cap` / `read_normal_temperature_cap` 直接解码保留值，
  没有验证整数和小数位是否合法。编码是低八位整数百分比、高四位十分之一百分比，
  不是整个十二位的二进制 0.1% 数值。例如原始 `0x3e8` 按这个格式会解出 2323，
  而非 1000；这种异常值可经上层截断表现为 100%。这是构造验证，不是故障机读数。
- 写入端没有统一拒绝越界值，可能将无效电量继续编码进保留区。
- 保留区的 SET/CLEAR 是锁存命令，原来使用可能省略同值写入的
  `regmap_update_bits`。现在对这三类保存函数使用强制写入的 `regmap_write_bits`，
  保留原来的掩码、编码、延时与硬件流程，确保同值也执行锁存写入。
- 原来的写后回读逻辑会被后续操作覆盖返回码：显示电量保存仍失败，随后读取常温
  电量成功，就可能最终返回成功。第二次写入也没有完整回读确认。
- 关机先保存电量、后停止更新任务，存在最后保存时仍有更新任务运行的窗口。

## 修复行为

- 只接受 0～1000 的有效电量及合法十分位；拒绝无效读数和写入，不把异常值截为满电。
- 正常历史值按原逻辑恢复。历史显示电量损坏时优先用有效的常温记录恢复；常温记录
  损坏时保留原厂使用有效显示电量的回退。只有首次上电或两份记录都无效才用已有
  启动 OCV 算法，不用固定百分比或简陋的线性电压估算替代正常库仑计。
- I/O 失败作为真实错误返回，不当作一次合法电量，不在总线错误时伪造满电。
- 保存最多尝试两次，每次回读确认，仍失败就返回错误；不增加无限重试。
- 关机先停止电量更新及相关任务，再完成最后一次保存。UVLO 工作可能自己触发
  `kernel_power_off()`，因此保留它的非同步取消，避免同步等待自己造成关机卡死。
- 更新任务检测 shutdown 标记后不再重新排队。

修复存放于 `devices/common/fuel-gauge-state.patch`，通过
`devices/common/fuel-gauge.py` 整体检查后应用。已接入 E5、T551M、M8 和通用
mainline 构建入口；不同源码版本、部分应用状态会明确报错，不静默漏打。

## 验证与限制

`python3 devices/common/test_fuel_gauge.py /path/to/linux-lts-e5` 通过：

- 提取补丁后的真实 C 函数编译执行，遍历全部 4096 种保留编码，其中恰好
  1001 种为 0.0%～100.0% 的合法值；验证原厂编码、重复同值保存及越界拒绝。
- 验证有效历史值不变、单字段/双字段损坏恢复、真实空电/满电、首次开机的温度
  补偿和总线错误处理。
- 验证首次写入失败后重试、持续写入失败、回读不一致、重试次数上限和错误传播。
- 验证关机先停止写者、UVLO 不同步等待自己、低电压关机策略不变。
- 验证补丁幂等及源文件不匹配时不产生部分修改。

使用实际 E5 ARM64 Clang 工具链与配置，`sprd_ump96xx_fuel_gauge.o`、
`sprd_fuel_gauge_core.o`、`charger-manager.o` 编译通过。

尚未生成或刷入新内核。若故障机两份保留记录都合法且确实为 1000，这组范围防护
无法单独解释是谁将它们写成满电；仍需区分错误满充判定、首次上电 OCV、bootloader
或其他系统改写。不能以本次离线测试宣称已经验证解决全部电量跳变。
