# 大流量后热点消失与复位恢复（2026-10-13）

## 实机故障

T551M 的 USB 管理和蜂窝连接仍可用，hostapd 进程也未退出，但热点无法使用。
现场内核日志在 32256.669 秒收到客户端 LUT 删除、BA 删除和离线事件；
随后下载残留包找不到客户端 LUT，每个包打印三条错误。
相邻包的日志间隔约 23 毫秒，其中一条输出约耗时 9.8 毫秒。
系统仍有 115200 波特率串口控制台，当前控制台级别为 4，错误级日志会同步输出。

32265.553 秒出现 `CMD_SET_IE` 超时，随后 WCN 断电复位，驱动留下
`hif->exit`，继续收到 Beacon 更新失败及发送队列 watchdog 超时。
驱动只向 Android 专用的 cfg80211 vendor 事件报告 `FW_ERROR`，最多重报五次；
现有 OpenWrt 没有对应恢复动作。手动 `wifi down radio0; wifi up radio0`
可重新加载固件、恢复热点，符合用户必须重新开关 Wi-Fi 的现象。

现场文件保存在本地 `work/t551m/wifi-fault-20261013/`，不纳入源码。
实际模块 build-id 为 `1f242aa6fc1014eacc089bbd8f14f0f3f106abf4`，
反汇编确认已有之前的 TX `cond_resched()`；本次不能归结为旧调度修复未加载。
最初为什么客户端断开，以及日志阻塞在本次固件超时中的贡献，尚不能仅凭
这份事后日志完全确定。下面同时处理明确存在的日志放大和恢复缺失。

## 公共修正

- 找不到 LUT 的正常丢弃诊断改为调试级；断开客户端的逐包丢弃日志改为
  `pr_debug_ratelimited()`，最终 TX 错误使用 `net_ratelimit()`。
  不修改 LUT 判定、skb 释放、带宽、队列大小或现有 ARP/DNS 分类。
- 真实 WCN 复位后的可睡眠工作首次报告时，额外发送一次
  `SC2355_RECOVERY=1` 的 ieee80211 change uevent，保留原 Android vendor 事件。
  不在原子通知回调中执行用户态命令，也不把普通客户端离线当作固件复位。
- 新增 `90-sc2355-recovery` 热插拔脚本，按实际 PHY 的设备路径匹配配置中的
  radio，只重开匹配的无线设备。关掉的 radio 不会被自动打开；重开前再次检查
  disabled，保留用户在恢复期间关闭无线的选择。
- 使用 flock 防止重叠恢复，60 秒内重复复位抑制自动重试，避免故障循环。
  Wi-Fi 关闭后等待 1 秒让 WCN 复位/SDIO 移除收尾；没有常驻轮询或常驻诊断。
- E5、T551M、M8 的内核准备共用 `wifi-common.py`，三个现有镜像更新入口
  也安装恢复脚本；干净 rootfs 构建通过公共 overlay 安装同一文件。

## 后续原因核对与 E5/M8 检查

原厂 Android 的 `sprd_report_softap` 反汇编也调用 `cfg80211_del_sta_sinfo`，
其 DWARF 中 SC2355 的 `evt_new_station` 同样只有 9 字节固定部分。
当前内核定义为连接标志、MAC 和 IE 长度，没有离线原因码。
`nl80211_del_station` 在用户态未提供原因码时默认使用
`WLAN_REASON_PREV_AUTH_NOT_VALID`（2），所以现场后续的 `reason:2` 不能
证明固件最初因认证异常踢掉客户端，也不能证明是手机主动离开。

17:43:39、17:45:02 又出现客户端离线，但没有固件断言，Beacon/查询应答仍正常；
用户确认是自己切换手机 Wi-Fi。这两次不计作自然掉线复现。
后续读到热点发送累计约 4.24 GB，仍没有新的固件复位。

E5、M8 的准备树原来也存在同样的 LUT/逐包 TX 错误输出和仅 vendor 事件
报告复位的代码；公共 iface/cfg80211 路径一致。两款均实际应用补丁，重复应用、
复位事件测试、注销清理测试、skb 所有权测试通过，模块编译和 BTF 生成成功：

## 首次接入跟进：AP 组播重复转发

继续抓取首次关联、CMD_TX_DATA 的报文头及固件应答，发现公共 SC2355
接收路径把网络字节序的 `eth->h_proto` 直接与 `ETH_P_IP` / `ETH_P_IPV6`
比较。在小端 CPU 上，IPv4/IPv6 都误入非 IP 分支：对于固件标记的 AP/GO
广播组播，驱动先复制并发回无线，再把原包提交网络栈，桥接 hairpin 随后
又转发一份。现场 DHCP、IPv6 邻居发现和 mDNS 的发送头部成对重复。

公共 `wifi-common.py` 修正为与 `htons(ETH_P_IP)` / `htons(ETH_P_IPV6)`
比较，IP 组播保留网络栈转发。没有关闭 hairpin、禁用 IPv6 或过滤 mDNS；
非 IP 转发和固件标记的单播 W2W 行为保持原样，也没有增加轮询。

`devices/test_wifi_rx_forward.py` 提取实际 RX 转发代码执行 C 测试：旧代码
可重现额外复制；修正版通过 AP/GO IPv4/IPv6、单播、ARP、复制失败和
STA 模式测试，启用 ASan/UBSan。三款准备树重复应用通过，模块编译成功：
