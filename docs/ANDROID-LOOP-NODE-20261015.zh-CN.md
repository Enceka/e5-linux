# Android 安装 loop 节点与清理修复（2026-10-15）

V50 首次续装在 `losetup` 报 `Permission denied`，第二次成功。实机检查发现首次安装留下了
`/data/local/tmp/.../work/loop31` 块节点，而 Android 的 `/data` 挂载带 `nodev`。
root 不能绕过该挂载限制；当时 SELinux 为 Permissive，并非其拒绝访问。
第二次 Android 已在 `/dev/block/loop31` 创建节点，镜像绑定成功，随后安装与 32 GiB 扩容通过。

根因是 `losetup -f` 可以分配新内核 loop 后立即返回，此时 ueventd 节点尚未出现。
原安装器把备用节点放到 userdata 下，因 `nodev` 无法打开。E5 原生 Magisk TF 入口也有同类逻辑。

两个仓库的 Android 安装路径已统一修正：

- 已有合法节点立即使用；新节点最多等待约 1 秒，不增加日常系统启动的轮询服务。
- 节点仍未出现时核对内核主次设备号，仅创建标准 `/dev/block/loopN`，设置权限并恢复 SELinux 标签。
- ueventd 并发创建节点可接受；异常索引、设备号及非块节点冲突则退出，不覆盖冲突文件。
- 不再在 `/data` 创建设备节点。标准 `/dev` 节点由 Android 管理，不生成安装器的私人别名。
- 只有本次绑定成功才允许失败清理解绑；卸载挂载点失败时保留 loop 并返回失败，避免误解绑其他进程或继续写 GPT／启动槽。
- MU300 镜像复验重新分配空闲 loop，不复用刚释放、可能已被其他进程占用的设备。
- E5 的 userdata 镜像复验显式绑定只读 loop；电脑入口上传公共 helper，打包清单包含并校验该依赖。

覆盖 MU300 桌面镜像生成、独立分区续装／重装、未分配空间写入，以及 E5／T551M／M8 公共
Magisk TF 固件转换与 userdata 镜像只读检查。initramfs 使用自身 `/dev` 的路径没有此次 `nodev` 备用节点问题。

回归测试使用临时文件和设备调用替身，覆盖节点立即出现、延迟出现、创建竞争、失败、非法设备号、
路径冲突、清理顺序、保留原错误码、未绑定不得解绑和卸载失败不得解绑。没有操作实机分区。
