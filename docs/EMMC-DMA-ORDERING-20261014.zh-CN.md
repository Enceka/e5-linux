# eMMC 文件损坏与 DMA 排序调查（2026-10-14）

## 当前结论

E5 已有直接证据表明本次并非单纯“重启少等几秒”：目录或 inode 表中出现了另一物理块的完整旧内容。同时，普通文件读写在 E5 和 V50 均触发 `mmc0: ADMA error: 0x02000002`，当时命令/数据 CRC 错误计数仍为 0。

修复展锐 SDHCI 的 DMA/MMIO 排序缺口后，E5 保持 HS400 enhanced strobe、200 MHz、8 bit，已通过 896 MiB 多缓冲写入及等量 O_DIRECT 读回、3584 次原子目录更新、重启后的 224 MiB 最新代数据校验，以及两遍离线只读 fsck。存储错误计数均为 0，运行时休眠仍启用。

V50 已按用户要求重新部署完整 OpenWrt：沿用现有 8 GiB 独立分区，没有再次缩容 userdata；重新从该 V50 的 Android 提取固件和运行库，一次性安装新内核及 52 个匹配的核心模块。完整普通镜像启动、网页登录页、热点、基带 AT、双卡配置和 V50 灯控进程检查通过；原热点设置、账号密码和 SSH 密钥保留。

在完整系统中，两轮合计 256 MiB 写入及等量 O_DIRECT 读回、1024 次元数据更新通过；正常重启后，64 MiB 最新代内容仍完全一致。当前 HS400 enhanced strobe、200 MHz、8 bit，运行时休眠为 auto/suspended，ADMA、超时、CRC、EXT4 计数均为 0。诊断启动镜像已替换为普通镜像，有界测试文件已清除。

这表示上述现场验证通过，不是任何硬件条件下永久不再损坏的保证。

## 原始损坏证据

E5 的第一次离线修复使用 e2fsck undo 文件保存了修复前的块内容。ADB 的终端路径插入了 CR，去掉每个 LF 前的传输 CR 后，undo header 和每个数据记录的 CRC32C 均通过，排除了把传输损坏误当磁盘损坏。

- `/opt/e5` 的 inode 为 1544，原 extent 指向文件系统块 14169。
- 块 14169 的 4096 字节，与 inode 表块 398 **逐字节相同**。
- SHA256：`36a7f5d0ffabfc5f1c8ddc669a2830cef818deaa1b4386dc7cbd6b1cc8b22992`。
- 后续旧驱动写入期间，另有三个 inode 出现了旧备份目录、备份文件的 inode 内容，导致目录/普通文件类型改变、校验和失效、多个 inode 引用相同的数据块。

因此，单纯延长 reboot 前 sleep 或反复 fsck 不能解释、更不能根治这种“位置正确、内容属于别处”的问题。文件系统或内存/DMA 路径、卡内地址映射都需要考虑；不能只凭块形态排除卡内故障。

## 本次修正

两仓库公共适配器：

- E5：`devices/common/emmc.py`，由 E5、T551M、M8 的内核准备流程共用。
- MU300：`upstream/port/emmc.py`。

展锐驱动覆盖了 SDHCI 的 MMIO 访问器，却全部使用 relaxed 访问。SDHCI 核心会先写 coherent ADMA 描述符，再写 COMMAND 启动 DMA；coherent 分配不保证这两个操作的先后关系。完成状态的读取也需要约束后续 DMA 数据读取。

本次改为与通用 SDHCI 访问器相同的 `readl/writel/writew/writeb`，保留展锐对保留寄存器、中断掩码和硬件复位位的特殊处理。没有加入轮询服务或逐次刷盘任务，没有降低总线模式、关闭写缓存或全局禁用运行时休眠。

这是一个独立可确认的驱动 API 排序缺口，E5 对照结果支持其有效；暂不宣称它是两种芯片所有历史损坏的唯一根因。

参考：[Linux MMIO 访问约定](https://docs.kernel.org/driver-api/device-io.html)、[DMA coherent 内存与内存屏障](https://docs.kernel.org/core-api/dma-api-howto.html)。原厂参考驱动也有 relaxed 访问，但其请求调度等路径不同，不能据此认为当前组合一定安全，也不能声称本次是照抄原厂已经存在的修复。

## 验证方法和边界

使用独立临时普通文件，不对原始分区做压力写，不操作 NV 或 Android 数据分区布局。每个 4 KiB 块携带文件编号、代数、块编号和逐字内容特征；fsync 后通过 O_DIRECT 读回，避免只读到页缓存而误报通过。

每轮四个并行写入者：总计 128 MiB 写入、128 MiB 读回，并发 512 次 fsync/rename 元数据更新。E5 修复前同组测试触发 1 次 ADMA 错误；修复后 7 轮没有新增错误。之后正常重启，并在未挂载根分区时执行两遍 `e2fsck -fn`，均通过；再恢复普通启动镜像、重启，校验全部 7 轮文件的最新代内容，共 224 MiB。

实际验证还包括内核/模块哈希、运行内核配置、蜂窝 IP/DNS、热点、屏幕服务、短信转发接口以及用户配置哈希。受旧驱动影响的程序、模块链接和流量状态已从校验过的载荷/保存数据恢复。

这些是有界测试，不是寿命或任何供电环境下永不出错的证明。已有损坏必须离线修复，排序修正不会自动恢复被覆盖的数据。

## V50 启动失败的另外两个问题

本次部署先遗漏了与新内核匹配的根分区模块，造成 BTF 类型校验失败，这是部署失误；配套模块补齐后仍未完整启动，因此不能把启动问题全部归咎于 BTF 或 eMMC 休眠。

随后在 Android 下只读核对根分区，发现 `sbin/procd` 等 7 个基础程序缺失，整个 `/opt/mu300` 目录也已脱离。71 个原程序及本机 Android 运行库的大部分内容可以在 `lost+found` 对应，说明“fsck 已通过”不等于系统文件齐全。`/sbin/init` 仍存在，旧启动检查却只检查这个小入口，因而继续 `switch_root` 后无法进入正常 procd；这解释了仅补齐模块依然无网页、无 SSH 的现象。

完整 `lost+found` 和原配置已留本地备份。遵照用户后续指示，没有执行逐文件恢复方案，而是重新制作干净系统、重新提取本机固件、写入已有 OpenWrt 分区，完成镜像回读、扩容至 8 GiB 和文件校验后才启动。没有修改 Android A 槽、GPT 或工厂 NV。原文件为何全部脱落尚不能从 fsck 结果精确定位到某一次写入；不能把“重新部署成功”当作 DMA 排序是唯一根因的证明。

## HS400 与 HS200

HS200 是合理的对照手段，但“降速后正常”不能独自区分 PHY 裕量、休眠恢复、命令调度和 DMA 排序。较慢模式也改变了时序关系，可能只是降低竞态出现概率。

本次优先保持 HS400。E5 已在 HS400 下通过上述验证；V50 也已独立通过完整系统启动、运行时休眠恢复和跨重启持久化验证。没有据社区描述将所有机型强制降到 HS200。
