# 提高蜂窝发射功率：定向查证结果

2026-10-17，承接 [功率控制评估](MODEM-TX-POWER-EVALUATION-20261017.zh-CN.md)。本轮继续只读分析，未发送功率设置命令。

## 目前能确切给出的结论

1. `AT+SPPOWERFB=0` 的完整命令能从原厂 HAL / RIL 的关闭功率回退分支确认。它是**取消额外功率回退**的命令，不是任意提高原厂最大发射功率的命令。未在本轮下发或测量实际效果；无法读取当前回退状态，因此不能声称当前设备执行后一定增大发射功率。
2. 实际 U30 Air 基带固件另有直接的发射功率控制候选；继续提取 E5、M8 的原厂工程应用后，还确认了 `SPMAXRFPWR` 的完整 NR 参数排列、应用输入范围和清除命令。但这属于射频工程测试入口，不能当作正常联网的增强开关。
3. 不把命令名字、测试形式返回 OK、参数被接受或 Speedtest 变快，当作物理输出功率已提高的证据。

## NR 最大 PA 功率分支

NR 命令名比较位于 `0x17d0a2a`，匹配后经 `0x17d0b0c` 到 `0x17d0fc4` 的处理分支。处理结构为三个数值参数：

```text
AT+SP5GCMDS="set nr max PA power",<参数一>,<参数二>,<参数三>
```

这只是已识别的解析结构，**不是可以照抄数值执行的提功率步骤**。

- 前两个参数各自都必须为 `1..23` 或 `255`，否则进入错误分支。具体比较见 `0x17d0fca–0x17d0fe2`。
- 代码并未允许把前两个参数设成 `26` 或 `30`。不能将这个入口宣传成可任意调整上限。
- `255` 是单独放行的特殊值；尚未确认是自动、保持、无效或其他语义，不能解释为 255 dBm 或解除限额。
- 第三个参数按一个字节读取，其模式含义未确认。
- `0x1326bb2` 转交到 `0x146a092`，后者将两个 32 位数值和一个字节放入消息，并以消息号 `0x2ee1` 发送到下游。
- 尚未完整确认两个功率参数各自对应哪一条射频路径、单位、特殊值、恢复方式与是否持久化；本轮不猜测两个参数就是两张 SIM 或两根天线。

因此，即使观察到最大值 23，也只能确认**解析器数值上界**，不能跳过单位和实际效果验证就直接向用户推荐数值组合。

## 新增实机只读查询

均通过已有 `/usr/libexec/unisoc-modem/at`、SIM 0 作用域执行，单条超时 3 秒，没有另开 tty。

| 查询 | 返回 |
| --- | --- |
| `AT+SPTXPWRCTL?` | `+CME ERROR: 65536014` |
| `AT+SPTXPWRCTL=?` | `+SPTXPWRCTL:(0-1),(0-1),(0-4),(),()`，随后 OK |
| `AT+SPPWRFBCFG?` | `+CME ERROR: 65536014` |
| `AT+SPPWRFBCFG=?` | `+SPPWRFBCFG: (0-2),(),()`，随后 OK |

`()` 没有给出有效范围或单位，不能补成猜测值。工具退出码 0 只说明完成了传输，`CME ERROR` 仍然是 AT 错误。

## 继续查证：原厂 EngineerMode 的精确功率设置入口

### 来源和交叉核验

直接提取本机留存的原厂 `system_ext/app/EngineerMode/EngineerMode.apk`，解析 `classes7.dex` 与资源表，没有从网络教程推测参数。

| 原厂应用 | APK SHA-256 |
| --- | --- |
| E5 | `45b959c8567e42ad18ab91be215ec4c2c463b22061e065b933daa1dff0ad35fb` |
| M8 | `1bab3fa951fb7e40fdf3d83b3bc1ac52b9988ee17214c718cbcbb26bc32a76a1` |

两份 APK 的 `NrSendPowerImpl`、`NrSendPowerPrefActivity` 和 `RfSendPowerImpl` 反编译结果分别相同。这个结论只覆盖应用端代码；不能据此认为两款机器或 U30 Air 的 CP 固件、射频硬件和校准值也相同。

### NR：`AT+SPMAXRFPWR`

`com.unisoc.engineermode.modules.hardware.rfsendpower.NrSendPowerImpl.setMaxPower()` 的实际格式为：

```text
AT+SPMAXRFPWR=16,1,1,<band>,<arfcn>,<power>,<bandWidth>,<antNumber>,<scs>,<modulationType>,<mimoType>,<group>,<dbmFlag>
```

所有选择框都直接传入从 0 开始的选项索引，而不是显示文字或其数值。原厂资源表对应如下：

| 字段 | 原厂应用实际传值 |
| --- | --- |
| `band` | 从已选 NR 频段名去掉 `NR_BAND_N` 前缀 |
| `arfcn` | 用户输入的频点字符串，不是自动读取当前服务小区 |
| `power` | 输入框原样传值；界面校验整数 `-43..27`，标签为 dBm |
| `bandWidth` | `0..11` 依次为 5、10、15、20、25、30、40、50、60、80、90、100 MHz |
| `antNumber` | `0=ANT0`、`1=ANT1`、`2=ANT2` |
| `scs` | `0=15 kHz`、`1=30 kHz` |
| `modulationType` | `0=CW`、`1=BSPK`（原资源拼写）、`2=QPSK`、`3=QAM16`、`4=QAM64`、`5=QAM256` |
| `mimoType` | `0=按 antNumber 开启天线`、`1=开启全部天线` |
| `group` | `0=SA`、`1=NSA` |
| `dbmFlag` | `0=positive dbm`、`1=negative dbm` |

原厂 `clearMaxPower()` 明确发送：

```text
AT+SPMAXRFPWR=16,1,0
```

以上是**原厂应用生成的工程命令与清除命令**，不是经过实测的联网提功率步骤。尤其注意：

- `27` 是应用的输入校验上限，不证明实际硬件能够输出 27 dBm，也不证明它高于该频段的原厂联网上限。
- 应用同时传 `power` 字符串和独立的 `dbmFlag`；负数与该标志如何组合，需要 CP 侧进一步确认，不能自行简化。
- 应用仅按返回字符串含 `OK` 判断成功，没有用功率仪证明实际输出。
- 该页面单独指定频点、调制方式和天线，包含 `CW` 连续波选项。这些证据将其定位为射频工程测试入口，不能把设置后的输出当成仍受正常联网调度的上行数据传输。
- 尚未追完这个 NR 页面之外的全部状态管理，也未证明固件强制检查飞行模式；不声称“应用必定自动进入飞行模式”。

### 旧制式：`AT+SPMAXRF` 与 PA 测试流程

`RfSendPowerImpl` 的生成方式是：

```text
AT+SPMAXRF=<bandEnum>,<operation>,<dbm>,<freq>,0,0
```

这个实现的枚举只有 GSM850/900、DCS1800/1900、TD19/21 和 WCDMA B1/2/5/8，**没有 LTE 频段枚举**，不能把 WCDMA 枚举 `7` 当作 LTE B7。

另外，原厂 `PATesterActivity` 确实有 LTE 的 `SPMAXRF` 测试序列。例如它的 `FDD_BAND1` 项包含发送、读取、停止三个步骤，采用固定频点和 23 的测试功率。该测试流程明确调用 `openAirplan()` 打开飞行模式，并在返回时关闭飞行模式；其用途是 PA 检测，不是正常联网时提高上限。这里不将这套测试序列包装成日常提功率功能。

### 其他候选没有凭名字补参数

对 E5、M8 两份 APK 的全部 DEX 扫描，未找到 `SPTXPWRCTL`、`SPPWRFBCFG`、`SPPOWERFB`、`SPPOWERBF` 或 `set nr max PA power` 的直接字符串调用。该结果不能排除其他系统服务、原生库或动态组装命令的调用，但目前没有应用端参数说明可用于补齐它们。

本轮还追查了 NR 工程消息 `0x2ee1`：消息长度分派确实为 `0x1c`，与前述最大 PA 功率发送结构一致；另外一些同立即数的命中实际是缓存长度，不能当作处理器交叉引用。尚未找到足以确认两个功率参数完整物理语义的接收端证据。

## 还没有的证据

- 没有确认当前设备正在被额外回退，也没有取消回退前后的功率对比。
- 没有完成 NR 最大 PA 功率参数的物理含义、恢复值及持久化行为验证。
- 没有证明任一候选可在正常联网时突破原厂最大发射功率。
- 没有将 U30 Air 固件中的私有参数套用到 E5、T551M、M8、F50 或 V50。上一报告只证明部分机型的 RIL 共用回退命令，不证明整套 CP 工程命令相同。
